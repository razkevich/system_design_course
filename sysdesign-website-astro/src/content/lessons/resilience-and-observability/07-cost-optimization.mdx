Most cloud overspend is not a mysterious tax. It is oversized instances, idle resources, chatty cross-AZ traffic, and a managed service you picked because it was easy. Cost optimization is an architecture skill: the same trade-offs as reliability and latency, with a monthly bill attached.

<KeyIdea>
Optimize the line items that dominate the bill. A week spent tuning a service that costs tens of dollars a month, while a database costs thousands, is the expensive kind of thrift.
</KeyIdea>

## Application-Level Rightsizing

A single-threaded service on a large multi-core instance is a common shape: you pay for CPU you never schedule. The same pattern shows up as oversized heaps, default connection pools, and frameworks that allocate everything at startup.

<IconGrid cols={2} items={[
  { icon: '☕', title: 'JVM and heap', body: 'G1GC is the default. Cap pause time (MaxGCPauseMillis) so GC spikes do not look like load and trigger scale-out. Size the heap from observed usage, not from a nervous default — many Spring Boot services run fine on a fraction of the heap they were given. Smaller G1 regions (8–16 MB) suit 1–2 GB microservice heaps better than the default.' },
  { icon: '🚀', title: 'Startup and idle work', body: 'Lazy bean initialization defers work until first use and can cut startup memory roughly in half. GraalVM native images trade build complexity for fast cold start and a smaller footprint — the right trade when you pay per start, as in serverless.' },
  { icon: '🔌', title: 'Connection pools', body: 'Oversized pools time out the database, which tempts an instance upgrade, which allows an even bigger pool. Most apps need on the order of 5–15 connections. Measure concurrent queries for a week before you buy more database.' },
  { icon: '📈', title: 'Profile in production', body: 'One bad query can be the compute budget. Continuous profiling belongs in the pipeline, not in the incident. The same idea holds outside Java: async runtimes, leak hunting, and container-aware CPU limits.' },
]} />

<Callout type="tip" title="Language changes the knobs, not the question">
Python (async I/O), Node (cluster mode and leak hunting), Go (goroutine pools and container-aware GOMAXPROCS), and modern .NET all have their own tunables. The decision is still: what did this process actually use?
</Callout>

### Disk class and database shape

Multi-AZ roughly doubles the database bill. That is the right insurance for the primary that serves customer traffic. It is a poor default for an analytics database queried twice a week — snapshots and a short restore window are cheaper. Read replicas that scale out and never scale in are the same mistake in another costume. Aurora Serverless v2 (and equivalents) scale both directions; a fixed replica fleet does not.

### Lifecycle, or storage that quietly compounds

<NumberCards items={[
  { title: 'Tier by access', body: 'S3 Intelligent-Tiering moves untouched objects to cheaper classes for a small monitoring fee. Typical savings are large relative to that fee. A hand-written lifecycle (Standard, then Infrequent Access, then Glacier, then Deep Archive) works when you know the access curve.' },
  { title: 'Expire snapshots and logs', body: 'EBS snapshots and old application logs accumulate forever unless a policy says otherwise. A common retention shape: daily for a week, weekly for a month, monthly for a year. Logs from six months ago do not belong in Standard.' },
  { title: 'Prefer object storage', body: 'S3 wins for backups, logs, static assets, and lakes. EBS when one instance needs low-latency block storage. EFS only when many instances truly need a shared filesystem — it costs several times EBS.' },
]} />

### The network line items people miss

Cross-AZ traffic is about a cent per GB. Health checks and chatty service discovery between zones add up. Keep a service and its database in the same AZ when the availability requirement allows it, and pay the cross-AZ tax only for the tier that actually needs multi-AZ.

NAT Gateway charges per GB on top of an hourly fee. A VPC gateway endpoint to S3 or DynamoDB skips that path. Interface endpoints have their own hourly cost; they pay for themselves once data processing is heavy enough that NAT per-GB dominates (on the order of a terabyte a month).

<Callout type="info" title="Managed is not laziness or virtue">
RDS and ElastiCache cost more than a VM because they do backups, failover, and patching. That is usually cheaper than a database specialist you do not have. A managed control plane for three services is the opposite trade.
</Callout>

Batch processing has the same shape. EMR Serverless fits infrequent Spark jobs and pays for a cold start. EMR on EKS fits a cluster you already pay for. Self-managed Spark on EC2 is the lowest cost per job when the jobs are large, frequent, and you can staff the ops.

## A Cost Review You Will Actually Hold

<NumberCards items={[
  { title: 'What went up?', body: 'Planned growth, or a surprise? Name the service. Ignore the twelve-dollar CloudWatch blip while a database jumped by hundreds.' },
  { title: 'What went down?', body: 'A real optimization, or traffic that disappeared? A cheaper bill is not automatically healthier.' },
  { title: 'What is new?', body: 'New resource types that were not on last month\'s bill. Catch them before they become the baseline.' },
]} />

Start with the free tools: Cost Explorer, Budgets, Compute Optimizer, Trusted Advisor, `kubectl top`, and an open-source allocator such as Kubecost. Paid platforms (CloudHealth, Datadog Cloud Cost, Spot, Cloudability) earn their fee when you need multi-cloud chargeback or executive reporting — not on day one.

<Callout type="warning" title="Stop optimizing when it costs more than it saves">
Developer time is usually the expensive resource. Saving a few hundred dollars a month by making deploys slower or incidents harder to debug is a false economy. Stop when the effort will not pay back in about half a year, when reliability or productivity drops, or when the service is a rounding error on the bill.
</Callout>

## Recap

- The bill concentrates in application waste, storage, and service choice. Work the large lines first.
- Rightsize from production profiles: heap, pools, disk class, and replica count.
- Tier storage, expire snapshots, and treat cross-AZ and NAT traffic as line items.
- Match the runtime to the traffic shape: serverless for spikes, containers and commitments for steady load, spot only where interruption is safe.
- On Kubernetes, scale down, split node pools, and size requests from observed usage — including ARM when your images allow it.
- Review monthly with three questions, and stop when optimization starts costing reliability or engineering time.
