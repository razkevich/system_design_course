Software architecture is a multi-dimensional thing. A single diagram can't capture every aspect — it ends up cluttered, contradictory, or both. **Architectural views** are different perspectives onto the same system, each tuned to a specific stakeholder concern.

This lesson is a tour of the views that pay off in practice: Philippe Kruchten's **4+1 model**, **quality views** that overlay structural concerns, Simon Brown's **C4 model**, and where enterprise frameworks fit in.

## The 4+1 View Model

Kruchten's 4+1 model is the classic answer to "how do I document this without my diagram becoming a spaghetti plate?" Four structural views, plus a unifying **Scenarios** view that ties them together.

### Logical view — what the system does

Functional requirements and the services delivered to end users. Domain objects, key behavioural patterns, the abstractions the rest of the team will reference in standups. We'll dig much deeper when we get to Domain-Driven Design.

<Callout type="tip" title="Interview-style example">
Designing an e-commerce platform, you might propose splitting along logical boundaries: an `OrderService`, a `PaymentService`, and a `CatalogService`, each responsible for its own slice of behaviour.
</Callout>

### Process view — the system in motion

The runtime architecture: processes, threads, services, queues, and how they talk. Where the logical view is a static picture of *what* the system is, the process view shows *what's happening at runtime*.

<Callout type="tip" title="Interview-style example">
"An API Gateway routes requests to ten replicas of `OrderService`, which calls `InventoryService` synchronously over REST, then publishes an `OrderCreated` event to Kafka for async processing by `PaymentService` and `NotificationService`." That's a process view spoken out loud.
</Callout>

### Development view — the codebase

The static organization of the code. Modules, libraries, packages, build artifacts, ownership boundaries between teams.

<Callout type="tip" title="Interview-style example">
A monorepo with `/services/order`, `/services/payment`, a shared `@company/auth-lib`, organized into `domain` / `application` / `infrastructure` layers. Team Checkout owns the order and payment modules.
</Callout>

### Physical view — software meets hardware

How software maps onto infrastructure: where things actually run, how they're networked, how resources are allocated.

<Callout type="tip" title="Interview-style example">
"Kubernetes on AWS EKS with autoscaling pods (3–20), Postgres on RDS Multi-AZ with read replicas, Redis ElastiCache, CloudFront CDN, all spread across three availability zones behind an Application Load Balancer." That's the physical view of a multi-tenant SaaS stack.
</Callout>

### Scenarios — the +1

Use-case walkthroughs that exercise all four structural views together. The consistency check — that logical, process, development, and physical describe the same system, not four different ones.

## Quality Views

The four structural views describe the *what* and the *where*. **Quality views** describe the *how well* — non-functional behavior cutting across structural views.

### Security view in detail

| Concern | What you draw |
| --- | --- |
| Perimeter | Firewalls, WAF |
| Transport | SSL/TLS termination, mTLS between services |
| Identity | OAuth/OIDC providers, JWT validation, session stores |
| Secrets | Vault, KMS, key rotation paths |
| Data at rest | Encrypted storage, per-tenant key isolation |

## Combining Views

Views can overlay productively. **Combined views** highlight strong, frequently-cited associations between two views — show the process view, then overlay security boundaries from the security view.

<Callout type="warning" title="Don't over-stack">
Combined views work best when the relationship is genuinely tight. Stack too many overlays and you end up with the spaghetti diagram you were trying to avoid. Two perspectives is usually the limit.
</Callout>

## The C4 Model

Simon Brown's C4 isn't an "architectural view" in the 4+1 sense — it's a **visualization** method. But it's how modern teams typically document architecture, so it earns a section.

C4 gives you four levels of zoom — progressively more detailed.

<NumberCards items={[
  { title: 'System Context', body: 'What is this system, and how does it fit into the world? One box, the people who use it, the systems it talks to. No tech details. Aimed at non-technical stakeholders.' },
  { title: 'Containers', body: 'Zoom in. A "container" = a deployable unit (web app, API service, DB, message broker). Shows the architecture shape and technology choices.' },
  { title: 'Components', body: 'Zoom into one container. Shows the major code building blocks behind well-defined interfaces. Should map to real groupings in the codebase.' },
  { title: 'Code', body: 'Zoom into one component. Class diagrams, interfaces, implementation shape. Often auto-generated from IDE; decays fastest as code changes.' },
]} />

<KeyIdea>
C4 + DDD pair beautifully. Container diagrams = bounded contexts as deployable units. Component diagrams reveal aggregates and domain services. Event Storming during discovery feeds the logical view directly.
</KeyIdea>

These frameworks are heavyweight. They earn their keep in regulated enterprises with hundreds of systems. For a single SaaS product team, **4+1 plus C4 is usually more than enough**.

## Recap

- One diagram can't show everything. Use multiple views, each for a specific concern.
- 4+1 model — Logical, Process, Development, Physical, plus Scenarios — covers structural concerns.
- Quality views (security, performance) overlay non-functional concerns.
- C4 is the modern visualization method: Context → Containers → Components → Code.
- Enterprise frameworks (ArchiMate, TOGAF) are heavy but useful at scale.
- Every view should help one stakeholder make one decision faster. If it doesn't, delete it.
