Figuring out what to build is often harder than building it.

Requirements engineering turns abstract business ideas into concrete specifications that engineering can deliver against. Skip this step and the system you ship will be technically excellent and functionally wrong.

Three types of requirements shape every architectural decision:

<IconGrid cols={3} items={[
  { icon: '⚙️', title: 'Functional', body: 'What the system does. Specific actions, features, capabilities that deliver business value.' },
  { icon: '📊', title: 'Quality', body: 'How well it does it. Performance, security, scalability, reliability — the non-functional characteristics.' },
  { icon: '🔒', title: 'Constraints', body: 'What limits the design. Technical, regulatory, organizational forces that bound the solution space.' },
]} />

## Functional Requirements: What the System Does

Functional requirements describe the specific actions, features, and capabilities that deliver business value. They look simple — *"the system should let users search for products"* — but the devil's in the details.

### The FAB structure: Feature, Advantage, Benefit

For each functional requirement, ask three questions:

<IconGrid cols={3} items={[
  { icon: '🔧', title: 'Feature', body: 'What can the system do? The technical capability.' },
  { icon: '💪', title: 'Advantage', body: 'What does the user get? The user-visible improvement.' },
  { icon: '🎯', title: 'Benefit', body: 'Why does the user want it? The underlying motivation.' },
]} />

**Example.** In a mobile payment system, **biometric authentication** is the feature. The **advantage** is removing PIN entry. The **benefits** are faster transactions and stronger security. All three matter — features alone get over-built; benefits alone get under-specified.

### Event Storming — surfacing implicit knowledge

Event Storming is a collaborative workshop technique for discovering business processes and the functional requirements that support them. Different colored sticky notes for:

<IconGrid cols={2} items={[
  { icon: '🟠', title: 'Domain events', body: 'Things that happen ("Order Placed", "Payment Completed").' },
  { icon: '🔵', title: 'Commands', body: 'Actions that trigger events.' },
  { icon: '🟡', title: 'Actors', body: 'People or systems initiating commands.' },
  { icon: '🩷', title: 'External systems', body: 'Outside services involved in flows.' },
  { icon: '🟣', title: 'Policies', body: 'Rules that fire when events happen.' },
  { icon: '🟢', title: 'Read models', body: 'The views people need to make decisions.' },
]} />

<KeyIdea>
The magic of Event Storming is that it surfaces *implicit* knowledge. Business experts often understand processes intuitively but struggle to articulate them. Engineers see technical possibilities but miss business nuance. Putting them in a room with sticky notes produces shared language and reveals dependencies neither side could see alone.
</KeyIdea>

### Lean Canvas for strategic context

Where Event Storming excels at process-level requirements, Lean Canvas provides strategic context — what problems are we solving, for which customers, with what unique value, through which channels and revenue streams. Use it to keep requirements anchored in business goals rather than feature wishlists.

### Architecturally significant requirements

Not all functional requirements are equal. A few force fundamental architectural decisions affecting the whole system. Watch out for these classes:

<IconGrid cols={2} items={[
  { icon: '🔌', title: 'Integration', body: 'Must talk to external systems.' },
  { icon: '⚡', title: 'Real-time', body: 'Must process events in real or near-real time.' },
  { icon: '🛡️', title: 'Security', body: 'Sensitive data, special compliance.' },
  { icon: '📱', title: 'Multi-platform', body: 'Multiple platforms or devices.' },
  { icon: '📈', title: 'Scale', body: 'Must scale to dramatically higher volumes than today.' },
]} />

<Callout type="warning" title="One innocent requirement can change everything">
"Users can view their activity history *even if they lose their phone*" sounds simple. But it forces server-side state, identity recovery, audit logging, GDPR considerations, and probably a sync layer. One sentence, six architectural commitments. Pay attention to "even if" and "what if" requirements — they're often load-bearing.
</Callout>

### Practical techniques

<IconGrid cols={2} items={[
  { icon: '🗺️', title: 'User journey mapping', body: 'Understand functional requirements in scenario context. Surfaces missing requirements; clarifies feature connections.' },
  { icon: '💬', title: 'Open-ended interviews', body: 'Detailed requirements after broad scope is understood. Ask open questions about goals and motivation, not closed questions confirming assumptions.' },
  { icon: '🎨', title: 'Mockups and prototypes', body: 'Make abstract requirements concrete. A simple prototype routinely surfaces dozens of implicit requirements that no document would capture.' },
]} />

## Quality Requirements: How Well It Works

Quality requirements (the non-functional kind) define how *well* the system performs its functions. Unlike functional requirements — which can usually be added incrementally — **quality requirements often demand architectural decisions made up front**.

### The invisibility problem

  left={{
    label: 'Visible until they fail',
    title: 'Why quality is overlooked',
    body: 'Users don\'t think about response time until pages load slowly. They don\'t think about security until there\'s a breach. They don\'t think about availability until the system is down.',
    accent: 'amber',
  }}
  right={{
    label: 'The fix',
    title: 'Make them explicit',
    body: 'Concrete, measurable scenarios. "Scalability" and "performance" are just words until you write a testable scenario.',
    accent: 'emerald',
  }}
/>

### Quality attribute scenarios

A complete scenario has six parts:

<NumberCards cols={3} items={[
  { title: 'Source', body: 'Who or what initiates the scenario.' },
  { title: 'Stimulus', body: 'The event requiring system reaction.' },
  { title: 'Artifact', body: 'The system component being tested.' },
  { title: 'Environment', body: 'The operational context.' },
  { title: 'Response', body: 'Expected system behaviour.' },
  { title: 'Response measure', body: 'Concrete, measurable success criteria.' },
]} />

<Callout type="info" title="Example: a search performance scenario">
*When 1,000 concurrent users (source) submit search queries (stimulus) during peak load (environment), the search service (artifact) returns results within 500 ms for 95% of requests (response and response measure).*
</Callout>

If you can't write a test for your scenario, it isn't specific enough.

### The Quality Attribute Workshop (QAW)

A structured method for surfacing and prioritizing quality attributes early.

<NumberCards items={[
  { title: 'Business presentation', body: 'Sets context and goals so technical teams understand which qualities matter to the business.' },
  { title: 'Architecture presentation', body: 'Stakeholders see the current or proposed design.' },
  { title: 'Scenario brainstorm', body: 'Generate quality attribute scenarios from all participants.' },
  { title: 'Consolidate and prioritize', body: 'Remove duplication; identify the most important attributes.' },
]} />

A few hours in a QAW typically saves months of expensive re-architecting.

### SRE: from requirement to operational reality

SRE provides a framework for measuring and managing quality in production:

<IconGrid cols={3} items={[
  { icon: '📏', title: 'SLI', body: 'Service Level Indicator — measurable metric (request latency, error rate, availability).' },
  { icon: '🎯', title: 'SLO', body: 'Service Level Objective — target for SLI over a window. "99.9% in <500ms over rolling 30 days."' },
  { icon: '💰', title: 'Error budget', body: 'Quantifies allowable unreliability within SLO. Ship faster while budget remaining; pause when burning down.' },
]} />

We go much deeper on SRE in Section 6. For now: SRE turns "we want it reliable" into something measurable.

<IconGrid cols={2} items={[

## Constraints

Constraints are the limits that bound your design space.

<IconGrid cols={2} items={[
  { icon: '🔧', title: 'Technical constraints', body: 'Existing systems, platform limits, technology choices the org has standardized on.' },
  { icon: '⚖️', title: 'Regulatory constraints', body: 'GDPR, HIPAA, SOC 2, PCI DSS — each shapes what data lives where, who sees it, how it\'s protected.' },
  { icon: '💰', title: 'Resource constraints', body: 'Budget, team size, available expertise, time to market.' },
  { icon: '⚙️', title: 'Operational constraints', body: 'Deployment windows, SLAs already in place, integration cadence with other teams.' },
]} />

<KeyIdea>
Constraints aren't obstacles to good design — they're inputs to it. The architectural skill is finding the *best* design that respects all constraints, not the *theoretical* design that ignores them.
</KeyIdea>

## Principles for Successful Requirements Engineering

<NumberCards items={[
  { title: 'Shared understanding', body: 'Between business stakeholders and technical specialists — not just a written spec passed back and forth.' },
  { title: 'Right techniques per type', body: 'Event Storming for processes. Mockups for UI. QAW for quality attributes. Don\'t use one technique for everything.' },
  { title: 'Collaborative workshops', body: 'Beat sequential handoffs. Everyone in the room produces better requirements than a chain of write-and-review.' },
  { title: 'Structured scenarios', body: 'For quality attributes. Vague is unmeasurable.' },
  { title: 'Systematic constraint identification', body: 'Don\'t let unstated constraints emerge halfway through implementation.' },
]} />

The goal isn't perfect requirements. It's shared understanding that survives the inevitable evolution of the system.

## Recap

- Requirements come in three flavors — functional, quality, constraints — and each needs different elicitation techniques.
- Functional describes behavior. FAB structure (feature/advantage/benefit) keeps focus.
- Event Storming surfaces hidden functional requirements through collaborative discovery.
- Quality requirements are usually invisible until they fail. Make them explicit through measurable scenarios.
- QAW and SRE practices give you a framework for prioritizing and operationalizing quality attributes.
- Quality attributes pull against each other; pick the right ones for your context.
- Constraints shape the design space; uncover them deliberately, not mid-build.
