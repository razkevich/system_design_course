In a monolith, method calls are cheap and reliable. In distributed systems, communication becomes a primary design concern.

Service-to-service communication is one of the load-bearing decisions in a SaaS architecture. The shape of communication determines how the system behaves under load, how it tolerates failure, and how easily it can evolve. The choices ripple through four properties at once:

  { icon: '🛡️', title: 'Reliability', body: 'Does the system stay stable under varying loads and failures?' },
  { icon: '⚡', title: 'Performance', body: 'Request latency and throughput.' },
  { icon: '📈', title: 'Scalability', body: 'Can it grow as load and demands increase?' },
  { icon: '🔧', title: 'Maintainability', body: 'Debuggability and ease of evolution.' },
]} />

## Synchronous: REST APIs

HTTP REST APIs remain the foundation. Simple, debuggable, supported everywhere.

<IconGrid cols={2} items={[
  { icon: '✅', title: 'Strengths', body: 'Simple to implement and debug. Universal tooling support. Immediate feedback. Clear success/failure semantics.' },
  { icon: '⚠️', title: 'Costs', body: 'Tight coupling. Latency propagation along call chains. Cascading failures.' },
]} />

<Callout type="pitfall" title="The cascading-failure trap">
A REST chain of A → B → C → D feels innocent. But if D slows down, B's threads pile up waiting on C, A's threads pile up waiting on B, and the whole stack stops responding. Long synchronous chains are one of the most common causes of multi-tenant SaaS noisy-neighbor incidents. Bound your timeouts and add circuit breakers.
</Callout>

## Synchronous: RPC and gRPC

RPC abstracts network communication so calling a remote function looks like calling a local one. Modern implementations (gRPC) layer in strong typing, code generation, binary serialization on top of HTTP/2.

<IconGrid cols={2} items={[
  { icon: '✅', title: 'Strengths', body: 'Strong contracts catch integration errors at compile time. Efficient binary serialization. Great fit for internal service comms where you control both ends.' },
  { icon: '⚠️', title: 'Costs', body: 'Browser support awkward. Opaque to humans. Requires schema management. Less universal than REST.' },
]} />

## Asynchronous: Message Queues

Message queues decouple services by letting them exchange data without waiting for an immediate response.

<NumberCards items={[
  { title: 'Send', body: 'Service A pushes a message onto the queue.' },
  { title: 'Continue', body: 'A keeps working — no blocking.' },
  { title: 'Process', body: 'Service B pulls the message when it\'s ready.' },
  { title: 'Survive failure', body: 'Messages persist when B is unavailable.' },
]} />

This pattern significantly improves system resilience. The cost is operational: you now have a queue to monitor, dead-letter queues to drain, consumer-lag dashboards to watch.

## Asynchronous: Event Streaming

Streaming platforms like Apache Kafka provide real-time data streams where services publish events as they occur, and other services subscribe to relevant streams.

<IconGrid cols={3} items={[
  { icon: '📊', title: 'Real-time analytics', body: 'Process user behavior as it happens.' },
  { icon: '👁️', title: 'System monitoring', body: 'Instrument infrastructure with structured events.' },
  { icon: '🔄', title: 'Data consistency', body: 'Propagate state changes across services through events.' },
]} />

The key shift is *publish to a log*, not *call a service*. Producers don't know who's listening; consumers can rewind, replay, and arrive late. Kafka gets a deep dive in Section 5.

## Asynchronous: Pub/Sub

Pub/Sub messaging lets services broadcast events to multiple interested parties without knowing who's listening.

```
              Order Service
                   │
        [purchase.completed]
        ↙       ↓        ↘
  Inventory  Email   Analytics
   Service  Service   Service
```

<KeyIdea>
Each subscriber processes the event independently. Add a new consumer (e.g., fraud detection) without touching any existing producer or consumer. Pub/Sub is what makes services genuinely decouplable in multi-tenant SaaS.
</KeyIdea>

## HTTP Protocol Evolution

<IconGrid cols={3} items={[
  { icon: '🐢', title: 'HTTP/1.1', body: 'Universal support. Connection-per-request issues. Verbose plain-text headers. The compatibility floor.' },
  { icon: '🐎', title: 'HTTP/2', body: 'Multiplexing, binary framing, header compression. Significant performance gains; ubiquitous now.' },
  { icon: '🚀', title: 'HTTP/3', body: 'Built on QUIC over UDP. No head-of-line blocking on packet loss. Best on lossy mobile networks.' },
]} />

For internal service-to-service on stable networks, HTTP/2 is the modern default. For client-facing on the public internet — especially mobile — HTTP/3 has the edge.

## Bidirectional: WebSockets

WebSockets provide bidirectional persistent connections between clients and servers.

<IconGrid cols={3} items={[
  { icon: '💬', title: 'Real-time chat', body: 'Instant messaging between users.' },
  { icon: '✏️', title: 'Collaborative editing', body: 'Synchronize document changes across users.' },
  { icon: '📊', title: 'Live dashboards', body: 'Push data updates without polling.' },
]} />

The trade-off is operational: load-balancing persistent connections is harder, connection management gets non-trivial at scale, reconnection logic needs deliberate design.

## Message Delivery Guarantees

<IconGrid cols={3} items={[
  { icon: '👻', title: 'At most once', body: 'Simple, but messages can be lost on system failures.' },
  { icon: '🔁', title: 'At least once', body: 'Default for most systems. Messages can duplicate. Consumers must be idempotent.' },
  { icon: '💎', title: 'Exactly once', body: 'Theoretically perfect. Hard to implement; often unnecessary. Whole lesson on this in Section 5.' },
]} />

<Callout type="info" title="Idempotency is your friend">
At-least-once + idempotent processing ≈ exactly-once for any practical purpose. Idempotency keys (Stripe-style), deduplication caches, or "this operation is naturally idempotent" — pick whichever fits.
</Callout>

## Order and Durability

  left={{

**Global ordering** is expensive and usually unnecessary. Most "we need ordering" requirements are actually "we need ordering per entity" — which partition keys give you.

## Choosing the Right Pattern

The most successful applications don't rely on a single pattern. They use the right one for each specific need:

<IconGrid cols={3} items={[
  { icon: '⚡', title: 'Sync patterns', body: 'User-related operations needing immediate feedback and high consistency.' },
  { icon: '🌊', title: 'Async patterns', body: 'Background processing, event notifications, fault-tolerance improvements.' },
  { icon: '🔀', title: 'Hybrid', body: 'Sync + async combined for optimal user experience.' },
]} />

<KeyIdea>
The skill is understanding the trade-offs and choosing based on the specific requirement, not chasing trends. Simple solutions often beat complex ones, especially in early stages.
</KeyIdea>

## Recap

- Communication patterns are architectural decisions shaping reliability, performance, scalability, maintainability.
- Synchronous (REST, GraphQL, gRPC) gives immediate feedback but creates tight coupling and risks cascading failures.
- Asynchronous (queues, streaming, pub/sub) decouples services and improves fault tolerance, at the cost of operational complexity.
- Most production systems mix patterns: sync where users wait, async everywhere else.
- Message delivery guarantees and ordering ripple through the system.
