ACID and BASE are two paradigms describing how databases handle concurrent operations and consistency. Understanding both is essential for choosing the right database — and for designing operations within whichever database you've picked.

## ACID: The Classic Guarantees

ACID describes what relational databases (and now many NewSQL systems) promise for transactions.

<IconGrid cols={2} items={[
  { icon: '⚛️', title: 'Atomicity', body: 'A transaction is all-or-nothing. Either every operation in it succeeds, or none of them are applied.' },
  { icon: '✅', title: 'Consistency', body: 'A transaction transitions the database from one valid state to another. Constraints (FKs, CHECKs) must hold before and after.' },
  { icon: '🔒', title: 'Isolation', body: 'Concurrent transactions don\'t interfere with each other. Different isolation levels offer different guarantees (next lesson).' },
  { icon: '💾', title: 'Durability', body: 'Once committed, the change persists — even through power loss, crashes, hardware failures.' },
]} />

<Callout type="info" title="ACID is about transactional integrity, not data correctness">
ACID doesn't promise your code is correct. It promises that if your code starts a transaction, all the operations in it either happen together or don't happen at all. Application bugs that violate business rules are not an ACID concern.
</Callout>

### The cost of ACID

Strong guarantees come at a price:

- **Locking and coordination** — concurrent transactions must serialize where they conflict.
- **Single-master writes** in many implementations — limits horizontal write scaling.
- **Slower than asynchronous alternatives** — durability requires fsync; isolation requires locks.

For some workloads, this is a fair price. For others, it's the wrong trade-off.

Those costs show up as concrete ceilings on a single primary. Trouble often starts somewhere between 100 GB and 1 TB, above roughly 10,000 requests per second, on tables of 10-100 million rows, or past a few hundred to a thousand concurrent connections. Buying the next machine size is a weak answer: doubling cores from 32 to 64 can about double the bill, on the order of $10,000 per month in a typical cloud shape, for about 1.4x more throughput. That is the wall BASE was built to walk around.

## BASE: The Distributed-System Alternative

BASE emerged as the alternative for systems that prioritize availability and scale over strict transactional integrity.

<IconGrid cols={3} items={[
  { icon: '🆗', title: 'Basically Available', body: 'The system remains available — possibly with reduced functionality — even during failures.' },
  { icon: '🌊', title: 'Soft state', body: 'State may change over time without explicit input, due to eventual consistency mechanisms.' },
  { icon: '⏳', title: 'Eventual consistency', body: 'Without further updates, all replicas eventually converge. No strict timing guarantee.' },
]} />

BASE accepts temporary inconsistency in exchange for availability and horizontal scalability. It's the natural model for distributed systems where strict ACID would require painful coordination.

BASE can loosen any of the four ACID properties. Atomicity becomes best-effort: eight of ten writes land and the caller reconciles the rest. Consistency allows a short broken invariant, such as balances that do not yet sum. Isolation allows concurrent operations to observe each other. Durability can accept loss, which is what an in-memory cache already does. The philosophy showed up around 2008 from systems at Amazon and eBay: during a partition, CAP says you give up either a consistent answer or an available one, and BASE keeps the available one.

ACID's "consistent" and a distributed system's "consistent" are different claims. The ACID word means invariants: the database enforces explicit constraints, and implicit business rules hold only if the transaction was written to preserve them. The distributed word means how soon a write is visible on other nodes.

That second axis is a spectrum:

1. **Linearizability.** One logical copy. Once a write completes, a later read returns that value or a newer one. It is a recency guarantee plus an atomic order.
2. **Sequential consistency.** Every node sees one order, and each client's own calls stay in program order. There is no real-time bound, so a node may observe that order late.
3. **Causal consistency.** If A happens-before B, every node that sees B has already seen A. Operations with no causal link may appear in different orders on different nodes.
4. **Eventual consistency.** If updates stop, every read eventually returns the last value. The model states neither a deadline nor which older value you may see meanwhile.

DynamoDB and Spanner sit on this spectrum per call: a strongly consistent read when the invariant needs it, an eventual read when it does not.

## When the Choice Matters

The key question is **what business invariants must hold**.

<IconGrid cols={2} items={[
  { icon: '💰', title: 'Hard invariants → ACID', body: 'Account balances must never go negative. Order quantities must match inventory. Bills must equal usage. Use ACID systems with serializable transactions.' },
  { icon: '👍', title: 'Soft invariants → BASE', body: 'Following count is approximately right. Like count is eventually right. Recommendation scores are eventually consistent. BASE systems handle this fine.' },
]} />

## Modern Systems Blend Both

Real production systems don't pick one paradigm. They use ACID where it matters and BASE where it doesn't, often in the same product.

<KeyIdea>
The architectural skill is **identifying which operations need which guarantees**. Payment processing → ACID. Notification delivery → BASE. User feed → BASE with read-your-own-writes optimization. Activity log → BASE with eventual consistency.
</KeyIdea>

## Sagas: ACID-like Workflows in BASE Systems

When a business operation spans multiple services (each with its own database), you can't use a single ACID transaction. The **saga pattern** chains local transactions with compensating actions.

```
1. Reserve inventory (ACID inside Inventory Service)
2. Charge payment (ACID inside Payment Service)
3. Schedule delivery (ACID inside Shipping Service)

Failure at step 3?
→ Compensate step 2: refund payment
→ Compensate step 1: release inventory
```

The result: business consistency through a sequence of local ACID transactions plus compensations, instead of one impossible distributed transaction. We covered this in [EDA, CQRS & Sagas](/lesson/architectural-patterns/eda).

## Recap

- ACID = Atomicity, Consistency, Isolation, Durability. The classic transactional guarantees.
- BASE = Basically Available, Soft state, Eventual consistency. The distributed-systems alternative.
- ACID is right when correctness matters more than availability. BASE is right when availability matters more than instant consistency.
- Modern systems blend both — ACID for hard invariants, BASE for everything else.
- Tunable consistency, async writes, read-your-own-writes, and sagas are the practical blending patterns.
