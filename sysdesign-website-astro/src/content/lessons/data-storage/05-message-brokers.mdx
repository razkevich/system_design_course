Message brokers are how loosely-coupled services exchange data without holding each other's network connections. They're the substrate that makes asynchronous architectures possible — and the source of half the operational complexity in distributed systems.

This lesson is the working vocabulary: queue vs. stream, push vs. pull, the major brokers, and when to use which.

## Two Paradigms

Most message systems fall into one of two categories:

<KeyIdea>
The choice between queue and stream isn't about technology — it's about whether you have one consumer or many. A queue distributes work; a stream broadcasts events.
</KeyIdea>

## Delivery Semantics

What guarantees does the broker provide about message delivery?

<IconGrid cols={3} items={[
  { icon: '👻', title: 'At most once', body: 'Messages may be lost on failure. Simple, but rare in production.' },
  { icon: '🔁', title: 'At least once', body: 'Default for most systems. Messages can be duplicated. Consumers must be idempotent.' },
  { icon: '💎', title: 'Exactly once', body: 'Theoretically perfect. Hard to implement; often unnecessary. We have a whole lesson on this.' },
]} />

<Callout type="info" title="Idempotency is the practical answer">
At-least-once + idempotent consumers ≈ exactly-once for practical purposes. Idempotency keys (Stripe-style), deduplication caches, or just "this operation is naturally idempotent" — pick whichever fits.
</Callout>

## Ordering

When does message order matter?

<Compare2
  left={{
    label: 'No ordering',
    title: 'Maximum throughput',

    accent: 'emerald',
  }}
  right={{
    label: 'Ordered by partition',

**Global ordering** is expensive and usually unnecessary. Most "we need ordering" requirements are actually "we need ordering per entity" — which partition keys give you.

## Choosing for SaaS

| Use case | Default choice |
| --- | --- |
| Background jobs / task queue | RabbitMQ or SQS |
| Event streaming, analytics, audit log | Kafka or Pulsar |
| Cross-region pub/sub | Google Pub/Sub or Pulsar |
| AWS-native, simple | SQS + SNS |
| GCP-native, simple | Pub/Sub |
| Both queue and stream needed | Pulsar (or Kafka with workarounds) |
| Hosted, low operational overhead | SQS / Pub/Sub / Confluent Cloud |

For most SaaS, the practical answer is:

- **SQS / Cloud Pub/Sub** for simple queue / pub-sub work.
- **Kafka (managed)** when streaming is core to the architecture.
- **Both** when you have both kinds of workloads — they coexist fine.

## Recap

- Two paradigms: queues distribute work; streams broadcast events.
- Major brokers: RabbitMQ (queues, rich features), Kafka (streaming standard), SQS / Pub/Sub (managed simplicity), Pulsar (modern hybrid).
- Push vs. pull — modern systems prefer pull for back-pressure.
- Delivery semantics: at-most-once, at-least-once (default), exactly-once. Idempotency is the practical answer.
- Ordering: partition-based ordering is the practical compromise. Global ordering is rarely actually needed.
- Common patterns: work queue, pub/sub fan-out, request/reply, routing, dead-letter, delay queues.
- Choose by use case; don't try to make one broker do everything.
