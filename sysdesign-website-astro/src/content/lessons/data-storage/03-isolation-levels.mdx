Transaction isolation is the **I** in ACID. It defines what one transaction can see of another transaction's in-progress work. The choice of isolation level is one of the most consequential decisions in transactional system design — and one of the most under-discussed.

This lesson covers the four standard SQL isolation levels, the anomalies each allows, and practical guidance for choosing.

## The Anomalies

Transaction isolation is defined by which **anomalies** can occur. Here are the classic ones, in order of severity:

  { icon: '🔁', title: 'Non-Repeatable Read', body: 'Transaction A reads a row, then reads it again later. The value has changed because B committed in between.' },

  { icon: '✏️', title: 'Write Skew', body: 'A and B read overlapping data, both check an invariant, both write. Each individually OK, but together they violate the invariant.' },
]} />

### What each level prevents

| Level | Dirty read | Non-repeatable | Phantom | Lost update | Write skew |
| --- | :---: | :---: | :---: | :---: | :---: |
| Read Uncommitted | ❌ | ❌ | ❌ | ❌ | ❌ |
| Read Committed | ✅ | ❌ | ❌ | ❌ | ❌ |
| Repeatable Read | ✅ | ✅ | partial* | ✅ | ❌ |
| Serializable | ✅ | ✅ | ✅ | ✅ | ✅ |

*Postgres prevents phantoms at Repeatable Read via MVCC; MySQL InnoDB allows them.

## Implementation Differences

The SQL standard gives names; databases implement them differently.

<Callout type="warning" title="Same name, different behavior">
"Repeatable Read" doesn't behave the same in Postgres and MySQL. Always read your specific database's isolation documentation. The SQL standard provides a name; the DB provides the semantics.
</Callout>

## The Snapshot Isolation Trap

Most databases' "Repeatable Read" or "Snapshot Isolation" is actually weaker than true serializable. The classic example is **write skew**:

```
Constraint: "At least one doctor must be on call."

T1 reads: Alice on call, Bob on call. (count = 2)
T1 thinks: "OK, I can take Alice off — Bob will still be on call."
T1 writes: Alice off.

T2 reads: Alice on call, Bob on call. (count = 2)  -- snapshot from before T1 commit
T2 thinks: "OK, I can take Bob off — Alice will still be on call."
T2 writes: Bob off.

Result: nobody on call. Constraint violated.
```

Both transactions read a consistent snapshot. Both wrote based on that snapshot. Neither saw the other. Snapshot isolation can't catch this — only true serializable can.

## Practical Guidance

<IconGrid cols={2} items={[
  { icon: '👤', title: 'Read Committed for most reads', body: 'Default in most databases. Right for the vast majority of read-only operations. Avoid the long held locks of stricter levels.' },
  { icon: '📊', title: 'Repeatable Read for reports', body: 'When you need a consistent view across multiple queries (e.g., end-of-day reports). All queries see the same snapshot.' },
  { icon: '💎', title: 'Serializable for invariants', body: 'When the operation must hold a business invariant that two concurrent transactions could violate (write skew scenarios). Be ready to retry on serialization failure.' },
  { icon: '🔒', title: 'SELECT FOR UPDATE for hot rows', body: 'Pessimistic row locking. Forces transactions to serialize on a specific row. Right for "decrement inventory" style operations.' },
]} />

## Optimistic vs. Pessimistic Concurrency

Beyond isolation levels, you have two strategies for handling conflict:

<Compare2
  left={{
    label: 'Pessimistic',

    body: 'SELECT FOR UPDATE / SELECT FOR SHARE. Block other transactions from touching this row until you commit. Good when conflicts are common.',
    accent: 'amber',
  }}
  right={{
    label: 'Optimistic',
    title: 'Work first, check for conflicts',
    body: 'Read with version number / timestamp. On commit, check if version still matches. If not, retry. Good when conflicts are rare.',
    accent: 'emerald',
  }}
/>

A typical optimistic update:

```sql
SELECT id, value, version FROM accounts WHERE id = 42;
-- compute new_value based on value
UPDATE accounts SET value = new_value, version = version + 1
WHERE id = 42 AND version = old_version;
-- if 0 rows updated, someone else modified it; retry
```

## Recap

- Isolation defines what one transaction sees of another's in-progress work.
- The classic anomalies: dirty read, non-repeatable read, phantom, lost update, read skew, write skew.
- Standard isolation levels: Read Uncommitted, Read Committed (default), Repeatable Read, Serializable.
- Same level name behaves differently across databases — always check your DB's specific semantics.
- Snapshot isolation isn't true serializable — write skew is the classic gotcha.
- Pick by use case: Read Committed for most reads, Repeatable Read for reports, Serializable for invariant-critical updates, FOR UPDATE for hot rows.
- For distributed systems: outbox, sagas, idempotency keys, ETags.
