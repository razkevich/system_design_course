Apache Kafka is the streaming standard. It powers event pipelines at LinkedIn (where it was created), Netflix, Uber, Airbnb, and basically every modern SaaS at scale. Understanding how Kafka actually works under the hood is what separates "I use Kafka" from "I run Kafka well."

## The Core Abstraction: Distributed, Partitioned, Replicated Log

Kafka is fundamentally a **commit log**: an ordered, immutable sequence of records. The clever part is that this log is **distributed**, **partitioned**, and **replicated** for scale and fault tolerance.

<IconGrid cols={2} items={[
  { icon: '📚', title: 'Topic', body: 'A named stream. Logs of related events. "user-events", "orders", "payments-completed".' },
  { icon: '🔪', title: 'Partition', body: 'A topic is split into N partitions. Each partition is an ordered, append-only log file. Parallelism unit.' },
  { icon: '🔄', title: 'Replica', body: 'Each partition has multiple copies on different brokers. One leader, others are followers.' },
  { icon: '🏢', title: 'Broker', body: 'A Kafka server. A cluster has many brokers. Each broker hosts some partition leaders and some followers.' },
]} />

```
Topic: "orders" (3 partitions, replication factor 3)

Partition 0:  [ msg0 → msg1 → msg2 → ... ]    Leader: Broker 1   Followers: Broker 2, 3
Partition 1:  [ msg0 → msg1 → msg2 → ... ]    Leader: Broker 2   Followers: Broker 1, 3
Partition 2:  [ msg0 → msg1 → msg2 → ... ]    Leader: Broker 3   Followers: Broker 1, 2
```

<KeyIdea>
The partition is the unit of parallelism. Within a partition, messages are strictly ordered. Across partitions, no ordering guarantee. This is how Kafka scales horizontally — more partitions = more parallelism.
</KeyIdea>

### Idempotent producer

When enabled (`enable.idempotence=true`), the producer attaches a sequence number to each message. The broker rejects duplicates from the same producer. Combined with `acks=all`, you get **exactly-once writes within Kafka**.

## Consumers

A consumer reads messages from topics. The key concepts:

<IconGrid cols={2} items={[
  { icon: '👥', title: 'Consumer group', body: 'A logical group of consumers sharing the work. Each partition is assigned to exactly one consumer in the group at a time.' },
  { icon: '📍', title: 'Offset', body: 'Consumer\'s current position in a partition. Stored in __consumer_offsets topic. Survives consumer restarts.' },
  { icon: '⚖️', title: 'Rebalance', body: 'When consumers join or leave a group, partitions are reassigned. Pause-the-world by default; cooperative rebalancing reduces this.' },
  { icon: '🔢', title: 'Parallelism cap', body: 'A consumer group can have at most N consumers, where N = number of partitions. More consumers than partitions = idle consumers.' },
]} />

### Consumer group example

```
Topic: "orders" (4 partitions)

Consumer Group "order-processor":
  - Consumer A → Partition 0, 1
  - Consumer B → Partition 2, 3

Consumer Group "analytics":
  - Consumer X → Partition 0, 1, 2, 3   (one consumer reads everything)

Both groups receive all messages independently.
```

This is what makes Kafka different from a queue: **multiple consumer groups read the same data independently**. Each group tracks its own position. Want to add a new pipeline tomorrow? Spin up a new consumer group; it reads from the beginning (or wherever you want).

## Replication and Fault Tolerance

For each partition, one broker is the **leader**; others are **followers**. All reads and writes go through the leader. Followers replicate from the leader.

### In-sync replicas (ISR)

A follower is "in-sync" if it has caught up with the leader within a configurable threshold. Only ISRs are eligible for leadership.

<Compare2
  left={{
    label: 'Healthy cluster',
    title: 'ISR includes all replicas',
    body: 'All followers caught up. Any can become leader on failure. Maximum fault tolerance.',
    accent: 'emerald',

  right={{

### Leader election

When a leader fails, a follower from ISR is promoted. With `unclean.leader.election.enable=false` (recommended), only ISRs can be elected — preventing data loss at the cost of availability.

## Storage

Kafka writes data to disk. The trick: **sequential disk writes are nearly as fast as memory writes** because of OS page cache and disk read-ahead.

## Operational Realities

<Callout type="warning" title="Running Kafka well is its own discipline">
Production Kafka requires understanding ZooKeeper (or KRaft in modern versions), JVM tuning, OS tuning, disk layout, network topology, monitoring (consumer lag, ISR shrinks, log size), capacity planning, and upgrade procedures. The flat learning curve is much steeper than "just use it."
</Callout>

## Recap

- Kafka is a distributed, partitioned, replicated commit log.
- Topics → partitions (parallelism) → replicas (durability).
- Producers choose partitions by key (ordered) or round-robin (max throughput). `acks=all` for durability.
- Consumer groups distribute work; multiple groups read the same data independently.
- ISR + min.insync.replicas + acks=all = production-grade durability.
- Kafka Streams / ksqlDB for in-Kafka stream processing. Connect for getting data in/out.
- Managed Kafka (Confluent, MSK, Aiven) is the right call for most teams.
- For SaaS multi-tenancy: topic-per-tenant for isolation, key-partitioning for scale, tier-based for hybrid models.
