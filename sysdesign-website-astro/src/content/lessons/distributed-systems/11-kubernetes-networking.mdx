Networking is the foundation of distributed Kubernetes systems. Understanding how packets actually flow lets you debug effectively, design resilient architectures, and reason about performance.

This lesson covers pod-to-pod communication, services, ingress, CNI plugins, and network policies — the layers that make K8s networking work.

![Kubernetes networking from the outside in: ingress, services, and pods](/images/k8s/kubernetes_front_image.png)

## The Networking Model

Kubernetes networking has four core principles:

<IconGrid cols={2} items={[
  { icon: '🆔', title: 'Each Pod has a unique IP', body: 'No port conflicts. No port mapping. App code doesn\'t need to know about deployment specifics.' },
  { icon: '🤝', title: 'Direct Pod-to-Pod communication', body: 'Pods talk via IP without NAT. Flat network topology.' },
  { icon: '🔄', title: 'Node-to-Pod communication', body: 'Nodes can reach pods directly. Required for kubelet, monitoring, kubectl exec.' },
  { icon: '👁️', title: 'Consistent IP visibility', body: 'A pod sees the same IP that other pods use to reach it. No internal/external IP confusion.' },
]} />

External access is opt-in: pods are private by default; you have to explicitly expose them via Services or Ingress.

## The Network Layers

A typical K8s cluster has multiple overlapping networks:

<IconGrid cols={2} items={[
  { icon: '🏗️', title: 'Cluster network', body: 'Underlying data center network or cloud VPC. Connects all nodes. Kubernetes doesn\'t manage it directly.' },
  { icon: '💻', title: 'Node network', body: 'Each node has its own IP on the cluster network. Used for node-to-node and node-to-API-server.' },
  { icon: '📦', title: 'Pod network', body: 'Pods get IPs from a separate CIDR (e.g., 10.244.0.0/16). Implemented by CNI plugin. Spans across nodes.' },
  { icon: '🆔', title: 'Service network', body: 'Virtual layer with ClusterIPs from another CIDR (e.g., 10.96.0.0/12). Not physical interfaces — managed by kube-proxy via iptables/IPVS.' },
]} />

![Pod-to-pod traffic across nodes, without NAT](/images/k8s/pod_communication.svg)

Direct pod-IP traffic (a headless Service, a StatefulSet peer, or a literal IP) never goes through a ClusterIP. The CNI bridge on the node is the switch:

1. **Same node.** Pod A sends to Pod B's IP. The packet hits the CNI bridge on that node and is delivered to Pod B. It does not leave the machine.
2. **Other node.** Pod A sends to Pod C's IP. The bridge hands the packet to the node network. The CNI either encapsulates it (VXLAN and similar overlays) or relies on cloud routes. The remote node's bridge delivers it to Pod C.

kube-proxy is not on this path. It only matters once the destination is a Service IP.

## CNI: The Plugin That Makes Pod Networking Work

Kubernetes itself doesn't implement pod networking. It delegates to a **CNI** (Container Network Interface) plugin.

When a pod is created, the CNI plugin:

1. Assigns an IP from the pod CIDR.
2. Creates a virtual network interface in the pod's network namespace.
3. Sets up routing rules so other pods can reach this one.
4. Applies network policies (if supported).

### Major CNI plugins

<IconGrid cols={2} items={[
  { icon: '🪶', title: 'Flannel', body: 'Simplest. Overlay network with VXLAN. No native NetworkPolicy support. Good for getting started; less common in production.' },
  { icon: '🛡️', title: 'Calico', body: 'BGP-based. Strong NetworkPolicy support. Performance-focused. Used by many enterprise deployments.' },
  { icon: '🕷️', title: 'Cilium', body: 'eBPF-based. Highest performance. Rich features: NetworkPolicy, transparent encryption, service mesh integration, deep observability. Default in many managed K8s distributions.' },
  { icon: '☁️', title: 'Cloud-native CNIs', body: 'AWS VPC CNI, Azure CNI, GCP CNI. Use cloud-native networking — pods get cloud VPC IPs directly. Best performance but tied to the cloud.' },
]} />

<KeyIdea>
Choose your CNI consciously. It affects performance, NetworkPolicy capabilities, observability, and what cloud features you can use. Cilium is becoming the modern default; Calico is the conservative choice.
</KeyIdea>

## Service Networking

Pods are ephemeral. Services provide stable virtual IPs that proxy to the current set of healthy backend pods.

### How Services actually work

```
Pod → ClusterIP (10.96.42.7)
        │
        ▼  (kube-proxy iptables/IPVS rules)
        │
   ┌────┴────┬────────┬────────┐
   ▼         ▼        ▼        ▼
 Pod IP1   Pod IP2   Pod IP3   Pod IP4
 (the actual current backend pods)
```

`kube-proxy` watches Services and Endpoints, maintaining iptables (or IPVS) rules on every node. It programs the kernel. It does not sit in the packet path itself.

A packet to a ClusterIP then becomes ordinary pod traffic:

1. Pod A sends to `backend-service`'s ClusterIP.
2. The local iptables or IPVS rules rewrite the destination to a ready pod IP (random or round-robin).
3. From there the packet follows the pod path above: CNI bridge, and the node network only if that pod is on another node.

A headless Service (`clusterIP: None`) skips the rewrite. DNS returns the pod IPs, and the client connects to one of them directly. That is how StatefulSet peers find each other.

## DNS

`CoreDNS` runs in every cluster, exposing service names as DNS records:

- `my-service.my-namespace.svc.cluster.local` → ClusterIP
- `pod-ip.my-namespace.pod.cluster.local` → individual pod (rarely used directly)

Pods get the cluster DNS in their `/etc/resolv.conf`, so a simple `curl http://my-service` (within namespace) or `curl http://my-service.my-namespace` (cross-namespace) resolves correctly.

## Ingress: HTTP/HTTPS Routing

Services give you Layer 4. Ingress gives you Layer 7.

```
                    [ Internet ]
                          │
                          ▼
                  [ Cloud Load Balancer ]
                          │
                          ▼
              [ Ingress Controller Pod ]
              (nginx, Traefik, ALB, etc.)
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
   [Service A]      [Service B]      [Service C]
   /api/*            /admin/*         /static/*
```

The Ingress resource is **declarative** routing config. The Ingress controller is the actual implementation — runs as pods, watches Ingress resources, configures itself accordingly.

Gateway API is the modern replacement for Ingress. More expressive, role-oriented:

## Network Policies

By default, all pods can talk to all other pods. **NetworkPolicies** restrict this.

```yaml
# Allow only pods labeled "app=frontend" to talk to "app=api"
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-from-frontend-only
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
```

<Callout type="warning" title="NetworkPolicies need a CNI that supports them">
Flannel doesn't support NetworkPolicies natively. You need Calico, Cilium, Weave, or another supporting CNI. Without enforcement, a NetworkPolicy resource is just metadata — it doesn't actually restrict anything.
</Callout>

For production, default-deny is the right baseline:

```yaml
# Block all ingress to all pods unless explicitly allowed elsewhere
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}
  policyTypes:
  - Ingress
```

## Advanced

Four mechanisms that show up once a cluster is large. They are not another CNI, and they are not the Service types above.

<IconGrid cols={2} items={[

  { icon: '🔒', title: 'cert-manager', body: 'Orders and renews TLS certificates for Ingress from Let\'s Encrypt or another CA. Renewal happens before expiry. Manual certificates are how clusters page someone at 3 a.m. because a secret lapsed.' },
  { icon: '🔢', title: 'Dual-stack', body: 'A pod can hold an IPv4 address and an IPv6 address. You need a CNI that implements it, a CIDR for each family, and application code that does not assume an IPv4 string. Existing IPv4 clients keep working during the migration.' },

## Recap

- Kubernetes networking has four principles: unique pod IPs, direct pod-to-pod, node-to-pod, consistent IP visibility.
- Four overlapping networks: cluster, node, pod, service. Each managed differently.
- CNI plugins implement pod networking — pick consciously (Cilium, Calico, Flannel, cloud-native).
- Same-node pod traffic stays on the CNI bridge. Cross-node traffic crosses the node network, then the remote bridge. A Service packet is rewritten to a pod IP and then takes that same path.
- Services proxy stable virtual IPs to current backend pods via kube-proxy and iptables/IPVS. Headless Services skip the virtual IP.
- EndpointSlices, ExternalDNS, cert-manager, and dual-stack are the scale-out pieces: smaller endpoint objects, automatic DNS, automatic certificates, and two address families.
- Ingress provides L7 routing; Gateway API is the modern replacement.
- NetworkPolicies restrict pod-to-pod traffic; need a CNI that supports them.
- Service mesh layers L7 networking concerns (mTLS, traffic management, observability) as infrastructure.
- Multi-cluster networking enables federated platforms across regions and providers.
