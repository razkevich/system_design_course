AWS has hundreds of services. Understanding how they compose is the difference between effective architects and people who randomly click around the console. This lesson is a working tour, organized by functional category — what each service is, what it composes with, and how a typical SaaS uses it.

## Foundation: Organizations & Accounts

<IconGrid cols={2} items={[
  { icon: '🏢', title: 'AWS Organization', body: 'Top-level container for multiple accounts. Centralized billing, policy inheritance, hierarchical management.' },
  { icon: '📁', title: 'Organizational Unit (OU)', body: 'Groups accounts within an Org for management. Common: Production OU, Development OU, Sandbox OU.' },
  { icon: '🔑', title: 'AWS Account', body: 'Primary boundary for billing and security. Multiple accounts → strong isolation between environments / business units / customers.' },
  { icon: '📜', title: 'Service Control Policies (SCPs)', body: 'Permission boundaries enforced at the OU/Account level. Even account admins can\'t exceed them.' },
]} />

A typical multi-account setup:

```
AWS Organization
 ├── Management Account (billing, IAM Identity Center)
 ├── Security OU
 │    ├── Audit Account
 │    └── Log Archive Account
 ├── Production OU
 │    ├── Workload-A-Prod
 │    └── Workload-B-Prod
 └── Development OU
      ├── Workload-A-Dev
      └── Sandbox
```

<Callout type="tip" title="When to pick what">
- **Lambda** for stateless, event-driven, infrequent compute.
- **Fargate (ECS or EKS)** for stateless services that need more flexibility than Lambda.
- **EKS on EC2** for stateful or scale-sensitive workloads, when you need full container orchestration.
- **EC2** when you need OS-level control or specialized instance types.
</Callout>

<IconGrid cols={2} items={[
  { icon: '🐘', title: 'RDS', body: 'Managed relational. Postgres, MySQL, MariaDB, Oracle, SQL Server. Multi-AZ for HA. Read replicas. Automated backups.' },

  { icon: '🌐', title: 'Neptune', body: 'Managed graph database. Property graph (Gremlin) and RDF (SPARQL). For relationship-heavy data — fraud detection, knowledge graphs, social networks.' },

## A Realistic SaaS Composition

Here's how a multi-tenant SaaS might compose AWS services:

```
                            [ Route 53 + CloudFront + WAF ]
                                          │
                                          ▼
                            [ ALB across 3 AZs ]
                                          │
                       ┌──────────────────┼──────────────────┐
                       ▼                  ▼                  ▼
              [ ECS Fargate ]    [ ECS Fargate ]    [ ECS Fargate ]
              (App service)      (App service)      (App service)
                       │                  │                  │
                       └──────────────────┼──────────────────┘
                                          ▼
                             [ Aurora Multi-AZ ]
                             (Postgres, with read replicas)
                                          │
                       ┌──────────────────┼──────────────────┐
                       ▼                  ▼                  ▼
                  [ Redis ]          [ S3 ]           [ DynamoDB ]
              (sessions/cache)   (file storage)    (high-throughput)

   [ Cognito ] ──→ [ API Gateway ] ──→ [ Lambda functions ]
   (user auth)     (public API)        (webhooks, async jobs)

   [ Kinesis ] ──→ [ Lambda ]    [ EventBridge ] ──→ [ Lambda / SQS ]
   (events in)     (process)     (cross-service)     (downstream)

   [ CloudWatch + X-Ray + CloudTrail ]   [ Secrets Manager + KMS ]
   (observability)                        (secrets + encryption)
```

This is a typical reference architecture. Most SaaS platforms run a variant of it.

<KeyIdea>
The skill isn't memorizing every AWS service — it's understanding how they compose. The same services appear in nearly every architecture; the choices are about which to pick and how they fit together.
</KeyIdea>

## Recap

- AWS resources hang off the Organization → OU → Account → Region → AZ hierarchy.
- Compute: EC2 (VMs), ECS/EKS (containers), Lambda (functions), Batch/Step Functions (orchestration).
- Storage: S3 (objects), EBS (block), EFS (file).
- Databases: RDS/Aurora (relational), DynamoDB (key-value), ElastiCache (cache), Redshift (analytics), Neptune (graph).
- Networking: ALB/NLB, API Gateway, CloudFront, Route 53, Transit Gateway, PrivateLink.
- Identity: IAM, KMS, WAF/Shield, Secrets Manager, Cognito, ACM.
- Messaging: SQS, SNS, Kinesis, EventBridge, MSK.
- Observability: CloudWatch, X-Ray, CloudTrail, Config.
- The skill is composition — knowing which services play together for which use case.
