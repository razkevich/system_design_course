Encryption is non-negotiable for any modern SaaS. The question isn't "should we encrypt?" — it\'s "where, how, and who manages the keys?"

This lesson covers the three states data lives in (at rest, in transit, in use), the encryption approaches for each, and the key management practices that make encryption actually meaningful.

## The Three States of Data

<IconGrid cols={3} items={[
  { icon: '💾', title: 'At rest', body: 'Stored data. Database, object storage, backups, logs. Encryption protects against media theft, unauthorized backup access, lost laptops.' },
  { icon: '🌊', title: 'In transit', body: 'Data moving across the network. Client-server, service-to-service. Encryption protects against eavesdropping, MITM, network compromise.' },
  { icon: '🧠', title: 'In use', body: 'Data being processed in memory. Encryption is much harder; emerging tech (homomorphic encryption, confidential computing). Mostly for highly regulated workloads.' },
]} />

For most SaaS, focus on at-rest and in-transit. In-use is the next frontier; not yet table stakes.

## Encryption in Transit

### TLS — The Foundation

TLS (Transport Layer Security) encrypts and authenticates network connections. Modern TLS is **TLS 1.2 or 1.3**; older versions (SSL 2/3, TLS 1.0/1.1) are deprecated and insecure.

Both sides present certificates. Used for service-to-service authentication where you don't want to rely on network position alone.

<Callout type="warning" title="Encryption at rest is a checkbox, not a strategy">
"At rest" encryption protects you from someone walking out with a hard drive. It doesn\'t protect you from an attacker with valid credentials — they get the data decrypted. Encryption at rest is necessary for compliance but doesn\'t replace good access control.
</Callout>

## Key Management

The hardest part of cryptography. Bad key management makes everything else moot.

### KMS — Key Management Service

Cloud-native KMS handles the operational complexity.

<IconGrid cols={2} items={[
  { icon: '🔑', title: 'AWS KMS', body: 'Managed keys. Hardware-backed (HSM available via CloudHSM). IAM-based access. Audit via CloudTrail.' },
  { icon: '🛡️', title: 'GCP Cloud KMS', body: 'Equivalent on GCP. Multi-region, HSM-backed, integrated with all GCP services.' },
  { icon: '🏰', title: 'Azure Key Vault', body: 'Equivalent on Azure. Plus secret storage, certificate management.' },
  { icon: '🪣', title: 'HashiCorp Vault', body: 'Self-hosted alternative. Strong fit for multi-cloud or specific compliance requirements.' },
]} />

### Envelope Encryption

The standard pattern in cloud KMS:

```
1. Generate a Data Encryption Key (DEK) — random AES key.
2. Encrypt the data with the DEK (fast — AES-GCM).
3. Encrypt the DEK with a Key Encryption Key (KEK) stored in KMS.
4. Store: ciphertext + encrypted DEK. KEK never leaves KMS.

To decrypt:
1. Send encrypted DEK to KMS.
2. KMS decrypts and returns DEK.
3. Decrypt data with DEK.
4. Discard DEK.
```

<KeyIdea>
Envelope encryption keeps the master key (KEK) in KMS hardware. Even if your application is compromised, the attacker doesn\'t get the KEK — they only get DEKs valid for a single dataset. Limit blast radius.
</KeyIdea>

Best practice: rotate keys regularly.

## Forward Secrecy

A property that limits the damage if your private key is later compromised.

<Compare2
  left={{
    label: 'Without forward secrecy',

    accent: 'rose',
  }}
  right={{
    label: 'With forward secrecy',
    title: 'Past sessions safe',

    accent: 'emerald',

/>

TLS 1.3 mandates forward secrecy. TLS 1.2 supports it via ECDHE cipher suites — make sure those are configured.

## Encryption in Use (The Frontier)

For highly regulated workloads where data must remain encrypted even during processing:

<IconGrid cols={2} items={[
  { icon: '🔒', title: 'Confidential Computing', body: 'TEEs (Trusted Execution Environments) — Intel SGX, AMD SEV, AWS Nitro Enclaves. Hardware-isolated execution; even cloud admin can\'t see the data.' },
  { icon: '🧮', title: 'Homomorphic Encryption', body: 'Compute on ciphertext directly. Mathematically beautiful; orders of magnitude slower than plaintext computation. Limited practical use today.' },
  { icon: '🔄', title: 'Multi-Party Computation', body: 'Multiple parties jointly compute over their inputs without revealing them. Banks computing aggregate statistics without sharing customer data.' },
]} />

These are emerging technologies. Most SaaS doesn\'t need them yet — but watch the space, especially if you serve regulated industries.

## Recap

- Three states: at rest, in transit, in use. Different threat models, different solutions.
- TLS 1.3 for in-transit. mTLS for service-to-service in zero-trust environments.
- Let\'s Encrypt or cloud-managed certs for public TLS. Internal PKI (cert-manager, Vault) for mTLS.
- At rest: TDE for DBs, transparent encryption for storage. Backups must also be encrypted.
- KMS for managed key handling. Envelope encryption is the standard pattern.
- Key rotation: automatic via KMS where possible, with rapid response procedures for compromises.
- Forward secrecy is mandatory in TLS 1.3, recommended in 1.2 (ECDHE cipher suites).
- Encryption-in-use (confidential computing, homomorphic encryption) is the frontier — watch but don\'t adopt prematurely.
