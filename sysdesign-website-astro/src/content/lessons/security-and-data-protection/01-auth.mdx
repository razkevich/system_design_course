## JSON Web Tokens (JWT)

JWTs are the standard format for tokens in modern web auth.

```
Header.Payload.Signature

eyJhbGciOiJSUzI1NiIs...     # header (algorithm, type)
.eyJzdWIiOiIxMjM0...        # payload (claims: user ID, expiration, etc.)
.SflKxwRJSMeKKF2QT...       # signature (HMAC or RSA, verifies integrity)
```

The payload contains **claims** like `sub` (subject = user ID), `exp` (expiration), `iss` (issuer), `aud` (audience). Plus custom claims (tenant ID, roles).

<IconGrid cols={2} items={[
  { icon: '✅', title: 'Pros', body: 'Stateless verification (server doesn\'t need to look up the user on every request). Self-contained — claims travel with the token.' },
  { icon: '⚠️', title: 'Cons', body: 'Hard to revoke before expiration. Long-lived JWTs are dangerous if leaked. Compromised signing key = catastrophic.' },
]} />

### Best practices

- **Short access tokens** (5-15 minutes) + **refresh tokens** (longer-lived, stored securely).
- **HTTPOnly cookies** for browser apps — prevents JavaScript from reading the token (XSS protection).
- **Asymmetric signing** (RS256, ES256) — server signs with private key, services verify with public key.
- **Validate every claim** — `iss`, `aud`, `exp`, custom claims you depend on.

For most SaaS, **start with RBAC**, layer in ABAC for nuanced cases (resource ownership, tenant boundaries), reach for ReBAC/PBAC when complexity demands it.

## Multi-Tenant Authorization

Tenancy adds another dimension to authorization.

<KeyIdea>
Every authorization check in a multi-tenant system has two questions: (1) does this user belong to this tenant? (2) within this tenant, what can they do? Forgetting question 1 is how cross-tenant data leaks happen.
</KeyIdea>

A typical pattern:

```
1. JWT carries tenant_id and user_id.
2. Every API call validates: user belongs to tenant? (else 403)
3. Every DB query includes WHERE tenant_id = ?
4. Authorization within tenant proceeds via RBAC/ABAC.
```

For added safety: **Postgres Row-Level Security (RLS)** can enforce tenant isolation at the DB level. App-level mistakes get caught.

## Common Pitfalls

<Callout type="pitfall" title="Things that go wrong">
- **Using OAuth for authentication** — OAuth is for delegation; OIDC adds the auth layer. Without OIDC, you get the access token but no verified identity.
- **Storing JWTs in localStorage** — vulnerable to XSS. Use HTTPOnly cookies.
- **Not validating tokens** — trusting the JWT payload without verifying the signature is the classic security bug.
- **Long-lived access tokens** — minimize blast radius of leaked tokens with short expiration + refresh.
- **Tenant ID from request body** — always derive tenant from the authenticated identity, never trust client-supplied tenant IDs.
- **Storing passwords with weak hashing** — use bcrypt, scrypt, or argon2. Never plain SHA, never plaintext.
</Callout>

## Recap

- AuthN = who are you? AuthZ = what can you do? Different problems.
- Modern auth: OIDC (on top of OAuth 2.0) for the protocol; JWTs for the token format.
- Authorization models: RBAC (simple, default), ABAC (flexible), ReBAC/PBAC (complex needs).
- For multi-tenancy: always validate tenant membership; use RLS for safety net.
- Don't build auth from scratch — use Auth0, Cognito, Clerk, or similar.
- Common pitfalls: OAuth-for-auth, localStorage for JWTs, long-lived tokens, weak password hashing.
